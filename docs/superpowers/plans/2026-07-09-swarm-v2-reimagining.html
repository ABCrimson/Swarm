SWARM v2 — from spectacle to the fastest agent harness on desktop

Benchmarked against Theo's T3 Code and T3 Chat: keep SWARM's Rust core and WebGPU identity, adopt the four architectural ideas that made T3's products win, and stop rebuilding what the labs already tune better than we can.

Date 2026-07-09 Baseline v0.10.0 (today's modernization pass — all gates green) Benchmark T3 Code v0.0.28 · 13.5k★ · T3 Chat

Context — why now

Today's audit fixed the "release candidate" fiction: 85+ findings, five crash-level runtime bugs, three charts rendering Math.random() as telemetry. The codebase is now genuinely evergreen (TS 7, Vite 8.1, Vitest 4, Rust 1.98-beta, pnpm 11) — but the architecture still predates the 2026 agent landscape. Theo shipped our exact category in the open: T3 Code is an MIT-licensed GUI for parallel coding agents, and its two load-bearing theses — wrap official harnesses, don't rebuild agent loops, and one ordered event stream, never polling — are both things SWARM currently does the opposite of. SWARM's custom Anthropic loop, ad-hoc Tauri events, and decorative-only topology are v1 thinking. The good news: our Rust + PTY + WebGPU foundation is exactly the substrate T3 Code lacks (it ships Electron 41).

The plan

Truthful, ordered core

Every pixel of UI state traces to one ordered, persisted event log — zero polling, zero fabricated data, replayable by construction.

  • Introduce an OrchestrationEngine in Rust: domain events (worker, session, AI, PTY) persisted to SQLite, in-memory read models derived from them.
  • Collapse today's ad-hoc emitters into a single ordered push bus (T3 Code's ServerPushBus pattern) over one Tauri channel; the frontend consumes exactly one ordered stream.
  • Replace remaining poll loops with typed receipts: worker-spawned, turn-quiescent, checkpoint-captured, stream-settled — UI and tests await receipts, never timers.
  • This resurrects session replay honestly (we deleted the dead replay UI today) — replay becomes "re-run the log", free.
~2 weeks · unlocks everything below

The harness pivot — SWARM's real product

Workers are no longer bare shells with a hand-rolled Claude loop — each worker is an official agent CLI (Claude Code, Codex, OpenCode) spawned in its PTY and driven over ACP/JSON-RPC.

  • Adopt Theo's thesis: labs tune harnesses to their models; wrapping claude-code, codex app-server, and OpenCode gets frontier agent quality + multi-provider support for free. Our PTY infrastructure already exists — we add the Agent Client Protocol layer in Rust, not another API client.
  • Keep lib/anthropic.ts streaming only for the orchestrator's own supervisor chat; delete the per-worker custom loop.
  • The topology graph gains real edges at last (today it draws Map-iteration order — we documented that honestly this morning): supervisor→worker delegation, worker→worker handoffs, all sourced from the event log.
~4–6 weeks · the differentiator: T3 Code's architecture at Rust-native speed, with a live GPU topology it cannot match

Safe parallelism + the ship chain

N agents never collide, every turn is reviewable, and finishing work is one click.

  • Git worktree per worker — T3 Code's proven isolation pattern, managed by the Rust core.
  • Turn-by-turn diff viewer as a first-class surface: checkpoint per turn (a receipt), Pierre-style diff per checkpoint, inline in the worker panel.
  • Ship chain: generate commit message → commit → push → open PR, one action per worktree.
  • Two-mode trust dial: Supervised (approval-on-request, workspace-write) vs Full-access — mapped directly onto Tauri capabilities + process sandboxing. One comprehensible switch, not a permission matrix.
  • Cost usage bar (T3 Chat's Feb 2026 pattern): one depleting/refilling meter per session fed by real token costs from lib/models.ts — multi-agent burn made legible.
~3 weeks · mostly UI over Phase-1 receipts

Local-first, headless-capable

Sessions open in <100ms from local SQLite; the swarm keeps working with the window closed.

  • Read models hydrate the UI instantly on launch — no spinners, T3 Chat's core speed trick, easier on desktop than it ever was on web.
  • Extract swarm-core as a headless daemon; the Tauri window becomes its first client. Remote access (Tailscale/SSH, a web client) becomes possible later without a rewrite — T3 Code's server/npx/mobile split validates the shape.
  • WebGPU particles stay — but every burst is driven by a real event from the bus (spawn, error, quiescence). Spectacle becomes signal.
~4 weeks · can trail Phase 3; daemon split is the only risky cut

Risks & kill-criteria

What would make us stop

  • Harness spike fails — if a 1-week ACP spike (drive headless Claude Code from Rust, stream a full tool-use turn into the existing UI) can't match the current loop's streaming UX, we halt Phase 2 and keep the custom loop as fallback. This spike is the go/no-go gate for the whole pivot.
  • Protocol churn — ACP/app-server interfaces are alpha-grade; we pin exact CLI versions (house rule) and wrap them behind one Rust trait so a breaking change costs one adapter, not the product.
  • Event-sourcing stall — if Phase 1 exceeds 3 weeks, we ship the push bus without SQLite persistence first (ordering is the value; durability can follow).
  • Scope gravity — the 97-milestone spec habit. Each phase ships independently; no phase starts until the previous one's verification passes.

Verification — how we'll know it worked

  • 0 polling loops in the frontend; every state change arrives as an ordered event (assert in e2e by replaying a recorded log).
  • Cold start to interactive session list <1.5s; 60fps sustained with 8 concurrent streaming workers (the spec's own budgets, now measurable against real streams).
  • An agent turn driven end-to-end through a real Claude Code CLI shows: live tokens, per-turn diff, checkpoint receipt, cost tick on the usage bar.
  • Kill the window mid-swarm → relaunch → session restores from the event log with zero lost turns (daemon phase: swarm never stopped).
  • Two workers editing the same repo never conflict (worktree isolation, verified in CI e2e).
